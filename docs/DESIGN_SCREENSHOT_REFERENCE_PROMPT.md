# Промт визуальных референсов для Codex

Используй этот промт перед любой задачей, где меняется внешний вид экранов VolleyPlay. Он определяет только **визуальный ориентир**. Функциональность, маршруты, права, данные и бизнес-логика всегда берутся из Git-контрактов проекта.

## Готовый промт

~~~text
Перед изменением UI сначала прочитай AGENTS.md, docs/implementation-prompts/README.md, docs/DECISIONS.md, docs/DESIGN_SYSTEM.md, docs/DESIGN_TOKENS.yaml, docs/SCREENS.yaml, docs/ROUTES.yaml, docs/ACTIONS.yaml и спецификацию конкретного экрана в docs/screens/.

Затем найди доступные локально или приложенные к задаче изображения-референсы. Используй их только для визуальной композиции, плотности, отступов, карточек, иерархии, табов и общего ощущения интерфейса.

ПРИОРИТЕТ ВИЗУАЛЬНЫХ РЕФЕРЕНСОВ

1. a_clean_mobile_app_ui_screenshot_white_light_back.png
   Основной референс всей light-first системы VolleyPlay.
   Брать за пример: белые и очень светлые поверхности, спокойную плотность, крупные читаемые заголовки, списки, avatar rows, search/filter controls, тонкие границы, чистую иерархию и нижнюю навигацию как визуальный приём.
   Не копировать названия вкладок и кнопок с изображения — использовать только текущие Git-контракты.

2. a_clean_mobile_app_ui_screenshot_light_theme_of.png
   Второй основной референс для списков игроков, карточек, горизонтальных подборок, счётчиков, chips и вторичных действий.
   Использовать как визуальный ориентир для profile/player-directory экранов и плотных списков.

3. детали_игры_на_пляжном_волейболе.png
   Референс для иерархии game.details: hero/обложка, название, дата и место, организатор, краткие правила, участники, вкладки/секции и sticky CTA.
   ВАЖНО: брать только композицию и приоритет информации. Не переносить тёмную палитру, неоновый зелёный, старые названия нижних вкладок, старые действия или старую продуктовую логику.

4. 1000043439.jpg
   Референс для экрана отдельного матча/результата: крупный счёт, команды/пары, статус матча, компактные переключатели разделов и информационная иерархия.
   Не копировать Google/browser chrome, футбольные сущности, тёмную тему и тексты.

5. 1000043437.jpg и 1000043438.jpg
   Референсы только для визуальной геометрии tournament bracket: горизонтальные стадии, карточки матчей, связи между раундами, selected round/stage и компактное отображение результата.
   Функциональность турнира брать исключительно из COMPETITION_FORMATS.yaml и TOURNAMENT_VISUAL_MAP.yaml. Не добавлять круговую, Swiss, группы+плей-офф, отдельный King of the Beach или любые форматы, которых нет в текущем Git-контракте.

6. профиль_тренера_по_пляжному_волейболу.png
   Дополнительный референс для trainer/public-profile экранов: hero profile block, ближайшее действие, информационные карточки, специализации, отзывы и связанные сущности.
   Использовать только структуру и информационную плотность. Тёмно-золотую палитру и старую нижнюю навигацию не переносить.

ПРАВИЛО ПРИОРИТЕТА ПРИ КОНФЛИКТЕ

При любом конфликте соблюдай такой порядок:
1. docs/DECISIONS.md и актуальные продуктовые решения;
2. YAML-контракты: SCREENS, ROUTES, ACTIONS, ACTORS, CAPABILITIES, ENTITY_SECTIONS, GAME_*, COMPETITION_* и другие относящиеся к задаче;
3. docs/screens/**/*.md;
4. DESIGN_SYSTEM.md и DESIGN_TOKENS.yaml;
5. существующий работающий код и тесты;
6. скриншоты — только визуальный референс.

Скриншот НИКОГДА не является основанием:
- менять route или screen_id;
- добавлять/удалять action_id;
- менять permissions;
- добавлять новый actor/role;
- менять модель данных;
- добавлять или удалять турнирный/игровой формат;
- менять payment/join/invitation/chat правила;
- создавать второй canonical screen, второй chat или второй bottom tab bar;
- возвращать уже удалённую функциональность;
- переписывать уже работающую реализацию без доказанной ошибки.

ПАЛИТРА И КОМПОНЕНТЫ

VolleyPlay остаётся light-first классическим сине-белым приложением.
Используй только semantic tokens из DESIGN_TOKENS.yaml. Не копируй hex/RGB из референсов и не добавляй hard-coded colors в экран.
Dark/system поддерживаются архитектурно, но скриншоты с тёмной темой используются только для композиции.
Переиспользуй общий UI-каталог. Не создавай локальные копии Button, Card, Header, FilterChip, TabBar и других shared primitives.

КАК РАБОТАТЬ С КОНКРЕТНЫМ ЭКРАНОМ

Перед кодом:
1. Определи screen_id и его Git-спецификацию.
2. Определи статус области: implemented / partial / placeholder / definition_pending / not_started / blocked.
3. Назови 1 основной и максимум 2 вторичных screenshot references.
4. Кратко выпиши, ЧТО именно берёшь из каждого изображения: например spacing, card hierarchy, bracket geometry, score layout.
5. Отдельно выпиши, ЧТО запрещено переносить из изображения из-за конфликта с Git.

При реализации:
- сохраняй текущие routes/actions/permissions;
- меняй только presentation layer и минимально необходимые shared UI primitives;
- не меняй бизнес-логику ради визуального совпадения;
- если изображение показывает функцию, которой нет в Git, не реализуй её;
- если Git требует функцию, которой нет на изображении, реализуй функцию по Git и стилизуй в духе ближайшего референса;
- если нужного screenshot-файла нет в текущем окружении, не угадывай его содержимое: отметь reference unavailable и используй DESIGN_SYSTEM + доступные изображения.

После реализации:
1. Через зарегистрированный iOS-плагин запусти экран в Simulator.
2. Сравни визуально со ссылочным screenshot только по выбранным visual traits.
3. Проверь safe area, 320–430 pt, 200% Dynamic Type, VoiceOver и keyboard, если применимо.
4. Запусти route/action/architecture validators и тесты затронутой области.
5. В отчёте явно напиши:
   - какие screenshots использованы;
   - какие визуальные признаки перенесены;
   - какие элементы сознательно НЕ перенесены из-за Git-контракта;
   - подтверждение, что routes/actions/permissions/business rules не менялись, либо список минимальных функциональных изменений, если они были прямо разрешены текущим рабочим промтом.

Не стремись к pixel-perfect копии чужого интерфейса. Цель — единый VolleyPlay: визуальная дисциплина из референсов + функциональная истина из Git.
~~~
