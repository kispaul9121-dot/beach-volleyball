# VolleyPlay — runbook для Codex с iOS-плагином

Каталог содержит **100 последовательных непересекающихся промтов**, пронумерованных `000–099`. Пакет рассчитан на работу в Codex с установленным iOS-плагином и подключаемым Supabase-плагином/MCP.

## Стартовая последовательность

Первые шесть промтов создают запускаемую основу приложения:

1. `000` — среда Codex, точное имя iOS-плагина, Expo-проект, backend baseline и правила работы;
2. `001` — базовый экран `Профиль`;
3. `002` — базовый экран `Игры`;
4. `003` — базовый экран `Чаты`;
5. `004` — базовый экран `Кэмпы`;
6. `005` — базовый экран `Настройки`.

После `005` приложение должно запускаться и позволять пройти по пяти нижним вкладкам, открыть базовые переходы и увидеть честные loading/empty/error/permission placeholders. Остальные промты развивают категории без повторного создания этих экранов.

## Как используется iOS-плагин Codex

Промт `000` обязан определить **фактическое** имя установленного iOS-плагина и способ его вызова через `@`-упоминание. Имя нельзя угадывать. Результат записывается в `docs/IMPLEMENTATION_RUNTIME.yaml`:

```yaml
codex:
  ios_plugin:
    mention: "@фактическое-имя"
    available: true
    capabilities: []
```

Каждый последующий рабочий сеанс:

- читает `docs/IMPLEMENTATION_RUNTIME.yaml`;
- вызывает зарегистрированный iOS-плагин, когда задача затрагивает UI, навигацию, simulator, keyboard, safe area, screenshots, VoiceOver или iOS build;
- не заявляет об успешной iOS-проверке без фактического результата плагина;
- при недоступности плагина помечает iOS-проверку `blocked`, но не подменяет её догадкой.

Официальные плагины Codex могут содержать skills и apps и вызываются через `@`-упоминание; доступ зависит от установленного плагина и прав рабочего пространства. Поэтому пакет не фиксирует выдуманное имя плагина.

## Быстрый backend

Для первой рабочей версии утверждён следующий путь:

- **Supabase Postgres** — основная база данных;
- **Supabase Auth** — регистрация и сессии;
- **Supabase Storage** — аватары и будущие вложения;
- **Supabase Realtime** — чат и обновления;
- **Supabase Edge Functions** — только операции с секретами, webhooks и внешними провайдерами;
- **Expo SQLite** — локальное хранение сессии и позднее read-only cache;
- собственного серверного приложения в первом проходе нет.

Supabase выбран потому, что имеет официальный Expo React Native quickstart, автоматически предоставляет Data API, поддерживает RLS и может управляться через Supabase plugin/MCP. Клиент использует только publishable key; service-role key никогда не попадает в мобильное приложение.

Промт `000` проверяет наличие Supabase plugin/MCP. Если он не подключён, агент не устанавливает и не авторизует его молча: он выводит требуемое действие и помечает backend как `blocked_by_connection`. Промт `010` создаёт или связывает проект после подключения.

## Архитектура приложения

Проект остаётся:

- React Native + TypeScript;
- Expo development builds;
- Expo Router;
- один общий код iOS/Android;
- iOS-first проверка через плагин, но без перехода на отдельную SwiftUI-кодовую базу;
- light-first классический сине-белый дизайн;
- dark и system поддерживаются архитектурно.

## Визуальные референсы

Перед любым промтом, который меняет внешний вид UI, дополнительно прочитать `docs/DESIGN_SCREENSHOT_REFERENCE_PROMPT.md`.

Скриншоты задают только визуальную композицию. Они не могут переопределять Git-контракты: `screen_id`, routes, `action_id`, permissions, actor-роли, модели данных, join/payment/chat правила и игровые/турнирные форматы. При конфликте функциональная истина всегда остаётся в архитектурных документах и тестах.

Основная светлая пара референсов:
- `a_clean_mobile_app_ui_screenshot_white_light_back.png`;
- `a_clean_mobile_app_ui_screenshot_light_theme_of.png`.

Для отдельных типов экранов файл DESIGN_SCREENSHOT_REFERENCE_PROMPT.md задаёт вторичные референсы и прямо перечисляет, какие элементы с них запрещено переносить.

## Источники истины

Перед каждым промтом прочитать `AGENTS.md`, этот runbook и перечисленные в промте документы. Приоритет:

1. `docs/DECISIONS.md`;
2. машиночитаемые `docs/*.yaml`;
3. `docs/screens/**/*.md`;
4. архитектурные документы;
5. работающий код и тесты.

При конфликте агент не угадывает. Он ограничивает изменения областью текущего промта, фиксирует конфликт и оставляет безопасную основу.

## Статус-зависимая работа

Допустимые состояния:

- `implemented`;
- `partial`;
- `placeholder`;
- `definition_pending`;
- `not_started`;
- `blocked`.

Правила:

- `implemented` — не переписывать, кроме доказанной ошибки;
- `partial` — сохранить работающую часть и дополнить только текущий сценарий;
- `placeholder` — сохранить публичный API и заменить только разрешённую часть;
- `definition_pending` — не придумывать бизнес-правила, оставить feature flag, типы или честный placeholder;
- `blocked` — не маскировать mock-логикой.

После изменения фактического состояния обновлять `docs/IMPLEMENTATION_STATUS.yaml`.

## Неповторяемость

Один промт — один ограниченный результат и один логический commit. Запрещено:

- повторно создавать пять базовых вкладок после `001–005`;
- расширять scope «заодно»;
- переделывать соседние модули без доказанной зависимости;
- создавать второй канонический экран, чат или tab bar;
- дублировать общий UI-компонент;
- возвращать удалённые сезоны или турнирные форматы.

Контрольные промты имеют `Audit-only` в тексте и не добавляют новую продуктовую функциональность.

## Формат завершения

Каждый агент обязан вывести:

1. статус до и после;
2. изменённые файлы;
3. выполненный сценарий;
4. тесты и команды;
5. отдельный результат iOS-плагина, когда он применим;
6. состояние Supabase migrations/RLS, когда затронут backend;
7. оставшиеся ограничения;
8. SHA логического commit, если commit доступен.

## Граница MVP

Не возвращать:

- сезоны и повторяющиеся игровые дни;
- круговую и швейцарскую системы турниров;
- `Группы + плей-офф`;
- отдельный турнир `Король пляжа`;
- двойное выбывание без нового решения.

Турниры: `single_elimination` и `full_placement`. Для 32 команд полное распределение содержит 80 матчей. `Король пляжа`, `Тунисский формат` и `Смешанные пары` — пользовательские названия разовой `Тунисской лестницы`.
